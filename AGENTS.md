# hermretro: guide for agents and contributors

hermretro is a Hermes Agent plugin for making Game Boy and Game Boy Color games for the ModRetro
Chromatic. The repository root is the plugin root. Hermes installs a plugin by cloning the default branch
(`main`) with no build step, and every file in it is checked by Hermes's install scanner. So whatever
reaches `main` is exactly what users run.

This guide holds the rules, the commands and how work lands. Deeper references are in `docs/dev/` and the README.

## Map

| Path | What it is |
|---|---|
| `__init__.py`, `plugin.yaml` | The plugin's entry point and manifest (tools, hooks, RPCs, version) |
| `backend/` | Python backend, one folder per feature: `broker/` (the broker process, engine workers), `hermes/` (everything that touches Hermes), `setup/`, `library/`, `assets/`, `history/`, `player/` (the browser player server), `system/` (locations, Linux/macOS differences) |
| `engine/` | `modretro-chromatic/`, the vendored ModRetro engine, and `pins/<version>/` (its tool contracts and file manifest) |
| `page/` | Source of the Hermes Desktop page and the player frame script: `app/`, one folder per page under `pages/`, `shared/`, `frame/` |
| `desktop/plugin.js`, `player/frame-shim.js`, `page/app/rpc-names.js` | Generated by `tools/bundle/bundle.mjs` and committed |
| `player/`, `skills/`, `profile/` | The browser player and device art; the skills the plugin gives the agent; the `hermretro` studio profile's files |
| `tests/` | Mirrors the code: `backend/<feature>/`, `page/`, `repo/` (repository-wide checks), `acceptance/` (real engine), `dev/`; `support.py` temp-folder helpers |
| `tools/` | `check.py` (every check), `dev/` (the development loop), `release.py`, `bundle/` (page build), `ci/`, `engine/`, `debug/`, `npm/` and `py/` (pinned dev tools), `layout.toml` (the folder map) |
| `docs/dev/` | `ARCHITECTURE.md` (and the full folder Map), `TESTING.md`, `DEBUGGING.md`, `CONTRACT.md`, `STUDIO-PAGES.md`, `ENGINE-UPDATE.md`, `INSTALL-SCANNER.md`, `RELEASE-CHECKLIST.md` |

Every file belongs to a folder in `tools/layout.toml` (a new folder gets a line there and in the Map of
`docs/dev/ARCHITECTURE.md`). Python and page source files warn above 400 lines and fail above 600.

## Commands

```sh
python tools/dev setup           # once per checkout or worktree: ruff and the npm tools (Node 22 or newer)
python tools/dev live            # Hermes loads this checkout (every linked profile); `live main` puts it back
python tools/dev reload          # after a backend change: re-import the plugin in the running gateway
python tools/dev watch           # rebuild the page on save; serves the live browser preview (prints its address)
python tools/dev rpc status      # one gateway RPC (plugin.hermretro.status)
python tools/check.py            # fast checks: unit, bundle, lint, page, scan
python tools/check.py fix        # automatic lint fixes and the Python formatting
python tools/check.py full       # plus the real-engine run (python tools/ci/prepare_toolchain.py first)
python -m unittest tests.backend.<feature>.test_<name>   # one module (unittest, not pytest)
node tests/page/<name>.test.mjs  # one page test (rebuild the bundle first after editing page/)
```

The development loop in full: `docs/dev/DEBUGGING.md`, "The development loop". CI runs the same checks plus a clean
install, the update from the newest release and, when a change touches `backend/`, `engine/` or the toolchain, the
real-engine run on Linux and macOS. Every failure ends with a `FIX:` line. Read CI with `gh pr checks <n>` and
`gh run view <run> --log-failed`.

## Rules that protect users

1. **Generated files.** Never edit `desktop/plugin.js`, `player/frame-shim.js` or `page/app/rpc-names.js` by hand.
   Change `page/` or the backend, run `node tools/bundle/bundle.mjs`, and commit the generated files with the sources.
2. **The engine is untouched.** Nothing under `engine/` changes outside a deliberate engine update
   (`docs/dev/ENGINE-UPDATE.md`).
3. **Install scanner.** `python tools/check.py scan` must say `safe`: one line rated high makes every install ask,
   one rated critical blocks installs. What trips it: `docs/dev/INSTALL-SCANNER.md` (instruction verbs aimed at
   agent configuration file names: write "this guide" instead).
4. **Linux and macOS, Apple Silicon and Intel.** Every change works on both. Locations come from
   `backend/system/paths.py`; a call that exists on one system only gets a branch for the other in the same place.
5. **One studio profile.** The plugin's tools, skills, hooks and prompt register only in the Hermes profile named
   `hermretro`; the page's chats go only there (`HERMRETRO_EVERY_PROFILE=1` in the gateway's environment lifts it
   while developing).
6. **Hardware.** The hardware tools (`flash`, `play`, `setup`, capture) stay behind the user's `hardware_enabled`
   setting and Hermes's approval prompt (`pre_tool_call` in `backend/hermes/hooks.py`); tests and CI never run them.
7. **Never the real Hermes home in tests.** A test that touches state calls `isolated_home(self)` from
   `tests/support.py` in `setUp`; `python tools/check.py unit` runs with an empty home and `TMPDIR` and fails on
   anything written there. The unit tests pass on a machine without Hermes.
8. **Notes stay local.** Plans, logs and evidence go in `notes/` (git-ignored); committed documents are those listed
   in `tools/layout.toml` `[docs]`.

Backend features declare their RPCs, tools, hooks and events in their own folder and reach each other only through
front doors and events (`docs/dev/ARCHITECTURE.md`, "Adding things" lists every place each piece touches).

## How work lands

1. **Agree first.** Look into the request read-only and come back with findings and a recommendation. Nothing
   changes until the owner says go. Their go says how it ends: **merge**, **review, then merge** (the default),
   **show me first** or **make a PR**.
2. **Branch.** A worktree beside the checkout, from `dev`: `git worktree add ../hermretro-wt/<topic> -b <type>/<topic>
   origin/dev`, then `python tools/dev setup` in it. Types: `feat`, `fix`, `docs`, `chore`. The main checkout stays
   on `dev`.
3. **Build and try it.** `python tools/dev live` in the worktree, `watch` in the background for page work, `reload`
   after backend edits; look at the result yourself (the live preview, or Hermes Desktop). `live main` when done.
4. **Check and open the pull request.** `python tools/check.py fix`, commit, `python tools/check.py`, push, then a
   pull request into `dev`. Title: `type(scope): what it does`, at most 72 characters; it becomes the squash commit
   and the release-note line. Body: the template's sections. No agent co-author or "generated with" lines.
5. **Review: one pass.** One reviewer agent, read-only, on the pushed head (the owner's choice of model; Codex
   `gpt-6.2-sol`, reasoning high). Its brief: the branch and exact head, the diff against `origin/dev`, what was
   approved, the rules above, and where to write findings: `Fix` (a defect, with the failure it causes),
   `Suggestion`, `Out of scope`, each citing `path:line`; nothing CI already enforces. Make every fix within what was
   approved, note the rest in the body's Review section. No second pass.
6. **Merge** when CI is green on the exact head (**All checks pass**): squash. GitHub auto-merge stays off. Then
   remove the worktree and its branch, and tell the owner what landed.

A failure that also fails `main` (an advisory, a broken dependency, flaky infrastructure) needs no approval: it is
fixed at once in its own pull request. This guide changes in the same pull request as any command or rule it describes.

## Releases (only when the owner asks)

`python tools/release.py`, run again after each step it stops at (exit 2 means waiting): the version pull request
when `dev` still says the last released version, CI on `dev`'s head, `main` fast-forwarded to it, the tag and a draft
release with generated notes. Read the draft, then `python tools/release.py --publish vX.Y.Z` (published releases
cannot change). `--rc` makes a release candidate and leaves `main` alone. Versions are patch-only (`0.0.N`); the
version lives only in `plugin.yaml`. Before a release, run `docs/dev/RELEASE-CHECKLIST.md` on a real machine (a
MacBook at least) and put its result in the draft's notes before publishing, or say there that it was not run.
